A conversation-first guide for process experts

Build the job, not the prompt.

If you can train a thoughtful new colleague, you already have the most important ingredient: judgment about what good work looks like. In a prepared workspace where Claude Cowork or a similar interface can invoke the pinned suite, use conversation to make that judgment explicit; Bench can then turn it into a durable worker with bounded capabilities, independent checks, and replayable evidence.

The honest answer

Useful? Yes. Fully self-service? Not yet.

Business experts can define a strong first agent and operate a bounded pilot. Today, they still need a prepared workspace and occasional platform help for executable checks, integrations, credentials, and production operation.

The business owner supplies the scarce part.

The outcome, tacit judgment, source precedence, exceptions, risk limits, examples, and the right escalation behavior.

The conversational builder should handle the machinery.

Turn the interview into reviewed files, invoke Bench’s Design → Build → Prove path, assemble the agent home, and show evidence in plain language.

The missing bridge is a product layer, not a smarter prompt.

We need a first-class conversational lifecycle adapter, no-code case and check authoring, governed connection setup, and an operator cockpit. The underlying control contracts are already unusually strong.

The business owner remains accountable for

Job choice, outcome, source authority, decision rules, exceptions, examples, risk limits, escalation, holdout labels, pilot thresholds, and whether the result is useful.

A platform steward still owns today

Suite/model setup, connector and credential provisioning, executable-check safety, runtime identity and confinement, schedules, budgets, monitoring, incident response, and high-stakes deployment approval.

The mental model

An agent is an operating agreement that can work.

A prompt describes behavior. A dependable agent also needs a durable outcome, trustworthy evidence, deliberately granted capabilities, and a separate definition of done. Each layer answers a different business question.

01 · outcome

What must become true?

Name the finished business state, not a vague activity such as “help with finance.”

02 · procedure

How should it reason?

Teach the normal path, exceptions, priorities, and reusable ways of working.

03 · evidence

What may it trust?

Identify authoritative sources, freshness, provenance, and conflict order.

04 · authority

What may it affect?

Separate reading, recommending, drafting, approved actions, and forbidden actions.

05 · proof

How do we know?

Check the result outside the worker; retain cases, verdicts, and run evidence.

Agent quality is multiplicative. A brilliant procedure with weak evidence, excessive authority, or a hollow check is still a weak agent.

Do not collapse the artifacts

Conversation, design, and worker are different things.

The Cowork thread is excellent for discovery and steering. It is a poor place to hide the only copy of a long-lived business process.

Before you build

Choose a narrow wedge into a real process.

The best first agent is not the biggest opportunity. It is the smallest useful job that gives you fast, trustworthy feedback.

Verify the workspace first.

A Cowork-style conversation can prepare business artifacts anywhere. A trustworthy build requires a dedicated workspace and a real path to the Bench suite.

Workspace

Connect one dedicated folder

Use a new agent project with test copies of data—not a broad home, Downloads, or shared production folder.

Runtime handshake

Verify the Bench path

Have the interface report where it executes, which suite version it reaches, and whether work is local, cloud, or managed.

Identity

Start without secrets

Use fixtures and test accounts. Do not paste tokens into chat or store credentials in the folder; connect OAuth later.

Source pack

Bring process evidence

Collect current policies, representative cases, existing outputs, known failures, and the names of decision owners.

Workspace handshake
Use this dedicated connected folder for the agent project. Before authoring anything, perform a read-only environment check: report where this task executes, whether the pinned Bench suite is available, the Bench and Agent versions, the workspace path, the current model boundary, and which folder, network, connector, and shell capabilities are available. For credentials, report only whether a capability exists and its resource, account identity, and scope—never inspect or print a token, secret, cookie, header, or environment value. Do not install software, authenticate, write outside this folder, or widen permissions. If the full suite is unavailable, stop after creating only the business worksheets and tell me what integration a platform steward must provide.
A connected folder is organization, not confidentiality.

Current local Agent runs use a full host shell inside Cage and may read anything available to that operating-system identity. Before any model-backed run with sensitive material, use a narrow account, container, or VM and scrub ambient secrets. The folder and Cage mainly constrain persistent writes and network—not host reads.

The first-job filter

Look for six signs of a good starting point.

1

Frequent

It happens often enough that a pilot will produce evidence in days or weeks, not quarters.

2

Bounded

It has a recognizable trigger, a finite set of inputs, and a clear handoff or deliverable.

3

Observable

A knowledgeable person can inspect the result and explain why it is right or wrong.

4

Digitally grounded

The required records, policies, and examples are available in files or connected systems.

5

Reversible

Early mistakes can be caught before they create financial, legal, customer, or operational harm.

6

Worth repeating

The saved effort or improved consistency is meaningful after setup, review, and operating cost.

Do not start here.

  • “Handle all of finance” or another organization-wide mandate
  • A process your team cannot explain consistently
  • Rare work with no realistic test cases
  • Irreversible payments, publishing, deletion, or access changes
  • A politically sensitive judgment with no accountable owner
  • A job whose only success signal is that the answer sounds good
Paste once into your Cowork-style builder
You are my Bench agent builder and operator. Use the installed Bench suite in the connected workspace; do not treat this chat as the agent's durable memory or source of truth.

Work conversation-first, but preserve the platform boundaries. Start in Bench Review mode. Interview me about the job, examples, exceptions, authoritative sources, actions, risks, and proof. Turn my decisions into a visible contract and stop for my review before admitting it.

For a recurring worker, use the full promotion path: Bench contract → Draft design → Build → Prove → Agent home. Keep definition, mutable work/state, the executable check, and controller evidence in separate write domains. Use Brief for reusable procedures, Context and Cite for sourced evidence, MCP and OAuth for reviewed connections, Action for external effects and May when policy requires exact human review, Cage for the worker action boundary, Trail for run inspection, Tend only where crash-durable execution is needed, and Hone only for a verified failed-then-passed recovery.

Begin with no network and read-only or draft-only business functionality. Report every ambient runtime capability, including full shell access, even when the job does not need it. Never store credentials in the agent home. Do not let model prose declare success. Show me the compiled home, the independent check, the holdout-case scorecard, the source/permission register, and every proposed authority increase. Stop when a missing choice, new authority, or consequential action needs me.

If your interface cannot run the installed suite or call a managed Bench integration, it can help prepare the business artifacts but cannot complete the trustworthy build path.

The guided build

Eleven stages, in the order that reduces rework.

Each stage gives the business owner a focused decision or review and the conversational builder one bounded platform job to perform. The prompts are starting points; answer follow-up questions with real examples.

01

Business owner decides · the accountable outcome

Frame one job as a finished state.

Name what triggers the work, which information is relevant, what must be produced, what success means, and where the agent must stop. Start from accountability, not personality.

When [trigger] happens, use [trusted inputs] to produce or do [result]. Success means [evidence]. Never [boundary]. Escalate when [condition].

Running example

When an invoice fails three-way matching, compare the invoice, purchase order, receipt, vendor record, and AP policy. Return the exception type, evidence, recommendation, and a draft message. Never approve or release payment. Escalate suspected duplicates, missing receipts, high-risk vendors, and exceptions over $10,000.

What good looks like

  • One trigger, not “whenever useful”
  • One primary deliverable or handoff
  • Named exclusions and stop conditions
  • A result another person can inspect
Why this connects.

The outcome will become GOAL.md; its observable parts become the check; its stop conditions become operating instructions; its risky actions become permission boundaries. A vague first sentence creates ambiguity everywhere downstream.

Ask your builder
Help me choose and frame one narrow first agent job. Interview me one question at a time about the trigger, inputs, result, success evidence, exclusions, and escalation conditions. Challenge vague words such as “good,” “appropriate,” and “handle.” End with one outcome sentence, a list of assumptions, and the three biggest reasons this may be a poor first job. Do not build anything yet.
Under the hood · Bench + Ask

The conversation is compiled in Bench Review mode into explicit deliverables, invariants, evidence, approvals, questions, and limits. Ask owns the model turn and exact event history. Work does not begin until the user reviews and admits the resulting contract.

02

Business owner decides · how judgment really works

Map decisions, especially the exceptions.

Policies usually describe the happy path. Your expertise lives in the moments when facts conflict, information is missing, a threshold is close, or the “usual” answer would be unsafe.

Ask contrastive questions

  • Why was this case approved but that similar one escalated?
  • Which source wins when policy and precedent disagree?
  • What does an expert notice that a checklist misses?
  • When is “I cannot determine this” the best answer?

Separate four things

  • Facts the agent observes
  • Rules the process requires
  • Judgment the expert contributes
  • Authority only a person or controller may grant
Ask your builder
Turn my real process into a decision map. Ask for the happy path, common exceptions, threshold cases, contradictory sources, incomplete inputs, suspicious inputs, and conditions that require a person. For each decision, record the evidence needed, the normal result, the escalation path, and the reason. Mark every unresolved disagreement instead of inventing a rule.
Under the hood · definition versus authority

The decision map shapes AGENTS.md and selected Brief skills. It cannot grant network, credentials, write access, approval, or completion authority. That separation prevents a well-written policy file from being mistaken for an enforcement boundary.

03

Business owner decides · what correct behavior looks like

Build the case library before the instructions.

Examples are not decoration. They are the beginning of the quality standard. Gather ordinary cases, hard cases, and cases where stopping is correct; then keep some unseen.

Teaching set

Use representative cases to explain the process and the reasoning behind expected outcomes. Include straight paths, common exceptions, and a few boundary cases.

Holdout set · withheld tests

Reserve cases the builder and agent do not see while authoring. Keep expected answers outside the worker-readable workspace or behind an external evaluation harness. Include missing, stale, conflicting, or maliciously phrased information and correct refusals.

Do not grade fluency.

A polished explanation can hide a wrong classification. Record the expected operational result, evidence, allowed action, and escalation—not merely an ideal paragraph.

Ask your builder
Create a teaching-case worksheet in the workspace with fields for case ID, inputs, expected result, required evidence, allowed action, required escalation, rationale, and risk. Help me add 10–20 varied cases. Create a separate holdout index, but keep its expected answers outside the worker-readable workspace or behind an external evaluation harness. If that separation cannot be enforced, mark the holdout contaminated and do not call its results unseen. Flag coverage gaps by decision branch and risk level.
Under the hood · cases become multiple checks

Mechanical expectations can become an executable bin/check. Case outcomes become an evaluation oracle. Qualitative judgment becomes a calibrated human rubric. Draft’s Prove stage mutates the built implementation and reports which defects the check fails to catch, so a weak check is less likely to accept a convincing but wrong result.

04

Business owner approves · the contract and design

Turn the interview into reviewed build artifacts.

Ask the interface to use Bench’s promotion path. First admit the exact build outcome. Then create a Draft project that says what the agent will do, who it serves, what it refuses, and how the build will be proved.

Review the Bench contract for

  • Concrete deliverables and preserved invariants
  • Acceptance evidence tied to the case library
  • Open questions and explicit assumptions
  • Approval boundaries and hard limits

Review the Draft design for

  • The intended user and recurring workflow
  • Definition, sources, tools, state, and outputs
  • Refusals, escalation, and authority model
  • Build check and how Prove will challenge it
There are two approvals because they answer different questions.

The contract says “build exactly this.” The design says “this is the system we intend to build and the proof it must survive.” Neither one is the running agent.

Ask your builder
Using our accepted outcome, decision map, and case library, start the full Bench promotion path in Review mode. Draft the exact outcome contract and show it to me in plain language before admission. After I approve it, create a Draft design for this recurring agent. Include users, durable definition, sources, tools, refusals, escalation, state, deliverables, an independent check, and a Prove plan. Stop on unresolved business questions; do not replace them with assumptions.
Under the hood · Bench → Draft

Bench’s /agent path creates and validates an ordinary Draft project. Draft’s Build loop composes Brief, Ply, and Ask; its executable check decides pass or not done. Prove mutates the implementation to expose gaps in that check. Today, the final bridge from a proved design to a complete Agent home still needs the conversational builder to orchestrate explicit platform commands.

Ask your builder
Build the Agent home from the accepted and proved design. Keep the files small and inspectable. Put standing outcome in GOAL.md, operating rules and escalation in AGENTS.md, only curated facts in MEMORY.md, reusable procedures in Brief-compatible skills, deliverables in work/, and progress in state/. Keep the executable check and controller evidence outside worker-writable roots. Run offline validation and show me the exact compiled home, authority, hashes, skills, tools, and check before any model-backed run.
Under the hood · Agent + Brief

agent new scaffolds the home, agent check validates its structure offline, and agent show prints the exact composition without calling a model. Structure valid does not mean agent ready: the fresh goal is placeholder text and the fresh check intentionally rejects. Brief owns skill linting and selection. If the job truly needs specialists, each child is another bounded Agent home with its own task, authority, check, work, and evidence—not a hidden copy of the parent conversation. The folder compiles into Ply and Ask rather than introducing a second hidden runtime.

06

Business owner approves · sources and blast radius

Connect evidence first; add action last.

For every source or tool, specify why it is needed, what it can read, what it can change, whose identity it uses, and what happens if it is wrong. Start at the lowest autonomy level that creates value.

01 · low risk

Explain

Read trusted material and summarize with evidence.

02

Recommend

Classify or propose a decision; a person decides.

03

Draft

Prepare a report, message, ticket, or change for review.

04

Act with approval

Bind a person’s exact decision to one exact proposed effect.

05 · earned

Bounded automation

Only reversible, well-measured actions inside a narrow policy.

For information

Context normalizes evidence from a selected connector. Cite checks exact evidence identities. MCP admits reviewed remote capabilities. OAuth keeps resource credentials outside the home and model context.

For effects

The worker writes an Action proposal. Action evaluates the exact proposal through controller policy; policy may allow, deny, or require one-shot May review. The controller rechecks relevant state before release. The connector records a receipt—or an explicit unknown effect that must not be retried automatically.

Capability and authority are not the same.

A tool appearing in a catalogue means the worker may know it exists. It does not mean a Markdown file, remote page, or model response can grant permission to use it consequentially.

Ask your builder
Create a source and permission register before connecting anything. For every source or tool, list its business purpose, authoritative fields, freshness, conflict priority, read scope, write scope, sensitivity, identity, reversibility, approval rule, and failure behavior. Propose the smallest capability set. Use Context/Cite for evidence, reviewed MCP capability folders for remote tools, OAuth outside the home for credentials, and Action for effects with May when policy requires exact human review. Keep the first pilot read-only or draft-only.
Under the hood · Cage is useful but not a complete machine boundary

Agent currently gives the worker a full host shell inside Cage by default, with persistent writes limited to work, state, and temporary space and network denied. The same operating-system identity may still expose host-readable files, environment values, credentials, processes, and programs. Cage is not a full confidentiality, credential, identity, resource, or per-task VM boundary. High-stakes unattended operation needs least-authority runtime defaults and the stronger external execution plane described in the platform roadmap.

07

Business owner judges · proof, not polish

Build a layered definition of good.

No single check captures the whole business outcome. Use fast mechanical gates, unseen cases, calibrated review, and live measures together. Make sure the check cannot pass merely because an output file exists.

Layer 1 · deterministic

Shape and invariants

Required fields, valid values, thresholds, evidence references, forbidden writes, and exact output location.

Layer 2 · case oracle

Behavior on holdouts

Classification, allowed action, escalation, and evidence match expected outcomes on unseen cases.

Layer 3 · human sample

Judgment quality

A calibrated expert reviews ambiguity, usefulness, tone, and whether cited evidence supports the recommendation.

Layer 4 · business

Downstream outcome

Correction rate, cycle time, avoided risk, adoption, cost, and the effect on the next person in the process.

A passing check is a claim about exactly what it checks.

It is not a general certificate of intelligence. Show the business owner which risks are mechanically covered, which are sampled, and which remain assumptions.

Ask your builder
Design the independent quality gate from our acceptance evidence and holdout cases. Separate deterministic checks, case-oracle expectations, human-scored judgment, and pilot business metrics. Show me exactly what bin/check proves and what it does not. Run Draft Build and Prove; use implementation mutations to challenge verifier coverage; then run our project-owned holdout suite through an external oracle. Run the shipped Agent corpus separately as a platform lifecycle smoke test, never as evidence of business-agent quality. Treat a model's confident explanation as no evidence of completion.
Under the hood · Ply + Ask + Draft + Agent eval

Ply runs the check before work and after candidate completion, sends rejection evidence back to the worker, and records sealed verdicts through Ask. Draft Prove looks for verifier gaps. Agent’s frozen corpus verifies deterministic lifecycle boundaries; project-owned holdouts and external oracles are still required for model quality and false-success measurement.

08

Business owner authorizes · controlled exposure

Pilot by widening one boundary at a time.

Do not jump from sample cases to unattended action. Compare the agent with real work while the cost of being wrong is still low and visible.

simulation→shadow mode→draft only→action with approval→bounded automation

Define the slice

  • One team, queue, customer group, or transaction type
  • A maximum value, volume, or risk class
  • A named owner and escalation destination
  • A start date, review date, and rollback path

Define launch gates first

  • Zero unauthorized effects
  • Every high-risk holdout escalates correctly
  • Routine-case pass rate meets the agreed threshold
  • Corrections and false confidence stay within bounds
Ask your builder
Create a controlled pilot plan that moves from simulation to shadow mode, then draft-only work. Name the population, volume, risk limits, owner, escalation path, success thresholds, stop conditions, review cadence, and rollback. Run the holdout suite before each authority increase. Keep live actions disabled unless I approve a separate, exact Action path.
Under the hood · replayable runs

Each Agent run keeps an Ask session and verifier receipts under the home’s controller evidence. Named checkpoints can resume a conversation, but the work tree and external check remain authoritative. Trail can list, search, show, window, follow lineage, and replay-check those sessions without creating a shadow history.

09

Business owner operates · one visible obligation

Separate running, waking, scheduling, and acting.

These look like one “autonomy” feature from the outside, but they have different failure modes. Keeping them separate is what makes the recurring worker understandable.

Run toward the standing goal

A goal run continues the durable obligation until the check accepts or a stop condition requires attention. A checkpoint resumes conversation, not a filesystem snapshot or an uncertain effect.

Wake only when something changed

An external schedule invokes the heartbeat. A cheap deterministic probe exits quietly before a model call when there is no work.

Supervise when interruption matters

Tend can make an ordinary local process crash-durable, with explicit lifecycle events and unknown states. It is not a distributed or exactly-once promise.

Inspect and approve outside the worker

Trail reads evidence; Action applies controller policy to effects and invokes May when human review is required; definition amendments remain reviewed exact patches. The worker does not own any of these verdicts.

Ask your builder
Create the operating plan for this home. Separate goal runs, heartbeat behavior, the external schedule, the cheap wake condition, checkpoint use, Tend supervision if needed, action policy and review, evidence review, incident handling, and unresolved-effect reconciliation. Add run budgets, periodic access recertification, and checks for source freshness and connector/schema drift. Show the owner exactly where to see current status, the latest check verdict, pending review, and run history. Do not hide cadence or authority in Markdown.
Under the hood · Agent + Tend + Trail + Action

agent run pursues GOAL.md. agent tick runs bin/wake before heartbeat work; cadence stays external. Tend may supervise a process durably. Trail reads Ask-owned history. Action treats a transmitted-but-unconfirmed effect as explicit uncertainty and forbids automatic retry.

10

Business owner governs · changes and learning

Improve from verified recovery, not accumulated chat.

A production agent is a managed business process. When a failure repeats, fix the process, cases, source, skill, or check deliberately; then rerun the holdouts before expanding scope.

Facts

Keep only small, current, human-reviewed facts in MEMORY.md. Raw run history remains in Ask sessions and is queried with Trail.

Procedures

Hone can propose a durable skill lesson only when replayable evidence shows a failure followed by a passing recovery. Exact admission remains a separate review.

Definition

The worker may propose a one-file patch, but Agent encodes the current definition and exact patch in a one-shot May request, rechecks both, then applies and revalidates.

Evaluation

Add every important escaped defect to the regression library, preserve holdouts, and compare quality, cost, latency, and escalation after each change.

Learning is a promotion decision.

A memorable failure is not automatically a true general rule. Preserve its evidence, prove the recovery, review the proposed lesson, and only then make it part of the next run.

Ask your builder
Review the latest failed or corrected runs through Trail. Classify each issue as a goal problem, instruction problem, source problem, tool/authority problem, state problem, or check problem. Do not append chat summaries to memory. Where one replayable run failed and a later run passed, prepare a Hone learning proposal for my review. For definition changes, prepare an exact Agent patch and show it before May approval. Rerun all regression and holdout cases after any admitted change.
Under the hood · Trail + Hone + May

Trail preserves Ask as the authoritative history. Hone replays both failure and recovery evidence and can prepare exact skill bytes without admitting them. Agent amendments bind an exact patch and current definition to a single-use May decision, then validate and receipt the change.

11

Business owner closes · authority and evidence

Retire the worker deliberately.

A forgotten schedule, connector, or credential is still authority. Retirement is complete only when new work is stopped, uncertain work is reconciled, access is revoked, and retained evidence has an owner.

Stop new work

Disable external schedules and event sources, stop or drain supervised runs, and suspend Action policies and connectors before changing the home.

Reconcile open work

Review pending decisions and every dispatched or unknown effect. Observe or resolve uncertainty; never turn retirement into an automatic retry.

Revoke access

Remove OAuth profiles, connector grants, service identities, browser sessions, and shared capability admissions that existed only for this worker.

Retain or delete by policy

Record the final definition/version, owner, reason, and last verdict. Preserve required receipts; archive or delete sensitive work/state under the organization’s retention rules.

Decommissioning is part of the design.

If the owner cannot name how to pause, revoke, reconcile, retain, and delete the agent, the operating model was never complete.

Ask your builder
Prepare a retirement plan for this Agent home. Inventory and stop every schedule, trigger, running Tend job, Action policy, connector, OAuth profile, browser/session grant, and shared capability used only by this worker. List pending reviews and unknown effects for human reconciliation; do not retry them. Propose the final evidence archive and the retention/deletion treatment for work, state, cases, and credentials. Record the final definition digest, version, owner, reason, last accepted verdict, and remaining obligations. Show the plan before any revocation or deletion.
Under the hood · retirement stays outside the home

Schedules, Tend supervision, OAuth profiles, Action policies, connectors, and evidence retention are controller or organizational responsibilities. Editing HEARTBEAT.md or deleting the folder alone does not revoke those external capabilities or settle a possibly-started effect.

The full platform path

Use every owner you need—never every tool at once.

“Full platform” means no guarantee is silently assigned to the model or the interface. Each consequential job has a narrow owner, and a phase invokes only the owners it needs.

Discover + admit

Turn intent into an exact obligation.

  • BenchConversational workbench, reviewed contract, visible authority, and final acceptance.
  • AskSelected model boundary and replayable event history; it makes no truth claim.
Design + procedure

Make the worker buildable.

  • DraftDesign → Build → Prove path with an executable check and mutation evidence.
  • BriefValidates and selects reusable Agent Skills without making them completion evidence.
Work + confine

Iterate without owning the verdict.

  • PlyChecked action loop; returns rejection evidence until the external check accepts.
  • CageCurrent host write/network boundary around model-authored actions.
  • AgentCompiles and runs the folder-shaped worker, checkpoints, specialists, proposals, and evidence roots.
Read + connect

Bring evidence and capabilities through explicit edges.

  • ContextNormalizes records from one caller-selected evidence connector.
  • CiteChecks exact evidence-reference and URL identity without pretending to judge meaning.
  • MCPDiscovers, digest-admits, calls, and serves protocol capabilities as programs.
  • OAuthRefreshes and passes one resource-bound credential to one exact child, outside the home.
Approve + affect

Keep intended real-world effects outside model authority.

  • ActionEvaluates a strict effect proposal through policy and, when required, one-shot May review before connector execution and typed receipts.
  • MayBinds one human allow or deny decision to one exact action/job request and spends a matching grant once; the caller owns state encoding and rechecks.
Operate + improve

Survive interruption without inventing history.

  • TendCrash-durable local process supervision with explicit unknown outcomes.
  • TrailRead-only search, projection, lineage, and replay checks over Ask history.
  • HoneReviewed procedural learning from replay-verified fail→pass recovery.

The Cowork-style interface sits above this map. It should translate business conversation into these explicit operations and render their artifacts. It must not replace their contracts with a hidden chat workflow or claim that the interface’s own sandbox, approvals, memory, or task history automatically supplies Bench’s proof.

Can business users really do this?

The substrate is strong. The self-service bridge is incomplete.

A capable conversational interface can hide command syntax. It cannot safely invent checks, source authority, credentials, deployment policy, or the product workflow. Those need explicit first-class experiences.

platform roadmap

The stronger execution plane

For consequential unattended work, finish the boundary around the worker rather than relying on interface-level confidence.

  • Signed capability locks and per-task sealed runtime
  • Workload identity and credential/effect proxies
  • Default-deny egress, quotas, and durable external evidence
  • Crash recovery that never retries an unknown effect automatically

Test ownership, not just creation.

  1. Ask a process expert to build an agent for a job they personally own.
  2. Give them an unfamiliar failure and see whether they can diagnose the bad layer: outcome, procedure, evidence, authority, state, or proof.
  3. Change a policy and see whether they can update the agent without regressing the holdout set.

Measure time to a testable home, unseen-case performance, safe escalation, permission mistakes, ability to explain a failure from evidence, regression after change, and whether user confidence matches actual quality. A polished demo is not the success metric; sustained ownership is.

Pilot readiness

Do not launch until every box has an owner.

Print this page or use the checklist during the final review. A “not applicable” decision should be explicit, not silently skipped.

The job is narrow and accountable.Trigger, result, evidence, boundaries, and escalation are explicit.
The real process is mapped.Normal paths, exceptions, thresholds, conflicting sources, and unknowns are covered.
Teaching and holdout cases are separate.The holdout set includes incomplete, stale, conflicting, and hostile inputs.
The contract and design were reviewed.Open questions were answered or deliberately left as stop conditions.
The compiled home was inspected.Definition, skills, tools, writable roots, authority, evidence path, and hashes are visible.
Sources and connections are governed.Priority, freshness, identity, sensitivity, scope, and credential handling are recorded.
The check proves something meaningful.Draft Prove challenged it; the limits of its claim are documented.
Every intended external effect uses controller-owned Action.Ambient host powers were removed or explicitly accepted; proposal, policy, conditional exact review, connector, receipts, and unknown effects have owners.
The pilot is a controlled slice.Population, volume, risk, thresholds, review date, stop rule, and rollback are set.
Operation is explicit.Run, wake, schedule, checkpoint, supervision, evidence review, and incident handling are distinct.
A named business owner remains accountable.The agent does not become the owner merely because it performs the work.
Changes trigger regression.New failures become cases; facts, procedures, definition, and checks follow separate review paths.
Retirement has a tested owner and path.Schedules, effects, access, evidence retention, sensitive state, and final accountability can be closed deliberately.
Final review prompt
Audit this Agent home against the pilot-readiness checklist in this guide. Use only the admitted definition, source/permission register, evaluation cases and results, compiled Agent view, and replayable platform evidence. For each item, report pass, fail, or unknown with the exact artifact that supports the answer. Do not infer safety or quality from model prose. End with the smallest next action that would resolve each fail or unknown, and stop before changing authority.

Scope and interface assumption

This guide assumes a Cowork-style environment that can work in a dedicated folder and invoke either a locally installed or managed Bench integration. Claude Cowork is one example, not a required provider. Its current product model supports delegated multi-step work, connected files and tools, visibility while work runs, parallel subtasks, and scheduled tasks; its execution and connector permissions remain an outer interface layer.
